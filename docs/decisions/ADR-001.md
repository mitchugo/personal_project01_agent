# ADR-001: Server-side authorisation is enforced independently of LLM behaviour

- **Status:** Accepted. **Implemented and tested** (Sessions 4–6): `app/gateway.py`, `app/authz.py`, tenant-scoped
  repositories, and `app/approvals.py`; exercised through `/chat` with mock and live models. See the verification plan below.
- **Date:** 2026-11-05
- **Related:** [architecture.md §5–7](../architecture.md), threats T-01 to T-05 in [threat-model.md](../threat-model.md)

## Context

The agent will call tools that read and change tenant data and create refund requests.
The tools are chosen and parameterised by an LLM. The LLM's output is shaped by:

- the user's message (which may be malicious — direct prompt injection),
- retrieved KB documents and ticket text (which may contain hostile instructions — indirect prompt injection),
- the model's own non-deterministic behaviour (it can simply be wrong).

So the model cannot be relied on to keep to tenant boundaries, respect roles, or decline
an unsafe action, however good the system prompt is. Prompt instructions are guidance to
the model. They are not a security control.

## Decision

1. **Identity is server-side only.** `tenant_id`, `user_id` and `role` come from the trusted
   request context (C2). Tool signatures exposed to the model will not include them. If the
   model supplies identity-like arguments anyway, the gateway ignores them and records the attempt.
2. **Every tool call passes through one policy enforcement point** (the tool gateway, C5),
   which:
   - validates arguments against a strict schema,
   - checks the caller's role against the permission matrix (default deny),
   - checks the target resource belongs to the caller's tenant,
   - writes an audit event for allow *and* deny decisions.
3. **High-impact actions need a human.** `request_refund` only creates a pending request.
   Approval is a separate, non-agent operation by a verified supervisor of the same tenant,
   who is not the requester.
4. **The system must stay safe if the model is fully compromised.** The design test is:
   *"If an attacker could make the model emit any tool call they want, what could they do?"*
   The answer must be: "only what the logged-in user is already allowed to do, with refunds still needing a human."

## Consequences

**Positive**
- Tenant isolation and role checks do not depend on prompt quality or model choice.
- Controls can be tested deterministically without a model (call the gateway directly).
- A single enforcement point is easier to audit and to cover with tests.

**Negative / costs**
- Duplicates some "rules" that also appear in the system prompt (the prompt helps usability; the gateway provides security).
- Every new tool must be registered with the gateway and given a permission-matrix entry.
- Refund flow is slower because of human approval. This is accepted.

## Verification plan

The decision counts as implemented only when tests demonstrate, without a live model:

- a tool call carrying another tenant's ID is not executed against that tenant (T-01, T-05),
- a role without permission is denied (T-02),
- a refund cannot reach "approved" without a different, same-tenant supervisor (T-04),
- allow and deny decisions are both audited, without secrets.

## Alternatives considered

- **Rely on the system prompt and model alignment.** Rejected: bypassable by prompt injection; not testable deterministically.
- **Let the model pass `tenant_id` and validate it.** Rejected: gives the attacker a parameter to manipulate for no benefit; the server already knows the tenant.
- **Per-tool ad-hoc checks without a central gateway.** Rejected for now: easy to forget a check on a new tool. May be revisited if the gateway becomes a bottleneck.
